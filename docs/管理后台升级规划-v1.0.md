# 慧共创管理后台升级规划 v1.0

日期：2026-11-10。状态：历史规划基线；后续已交付并部署 admin-ui-1.1.0，见 [交付记录](admin-ui-1.1.0/README.md)。规划条目是否完成应按交付范围逐项判断，不将整份规划视为全部验收通过。对应当前小程序 v2.3.3 的产品边界与视觉原则，后台独立版本管理。

## 1. 目标与范围

把现有平台管理工具整理成可日常使用的运营后台：看清运行状态、找到用户与任务、完成点数和权限操作、处理待核实任务、核对规则变更。优先改进现有功能的阅读与操作，不先扩充菜单或统计图。

平台后台面向明确授权的管理员。活动发起人、协作者、参与者继续在小程序操作；按 PRD 顶部已确认修订，不恢复组织者电脑工作台。公众号内容由用户自行复制发布，后台不增加自动发布功能。

共创与成绩共用身份，不代表平台管理员默认有权读取、编辑或导出所有学生成绩。本期不增加学生成绩列表、私人资料浏览或无接口支持的空入口。

## 2. 已核对的实际基线

| 项目 | 当前实现 | 升级处理 |
| --- | --- | --- |
| 入口与页面 | `/manage` 跳转 `/manage.html`；`backend/public/manage.html/js/css` | 保留可访问入口，整理布局与模块结构 |
| 管理员身份 | 独立账号密码登录、8 小时管理员会话；与微信用户会话分离 | 保留鉴权边界，完善过期/退出体验；不增加管理员自助注册 |
| 一级入口 | 概览、用户与点数、活动、AI 任务、规则与预算、审计、历史账号认领 | 前六项作为主导航；认领并入用户模块的次级入口 |
| 视觉 | 灰绿背景；正文 14px、表格 12px；大表格及整页配置表 | 改纯白主体、清晰字号、统一图标与间距 |
| 详情 | 多处直接显示整条记录的 JSON | 改为结构化抽屉；技术字段按需展开 |
| 列表 | 大多整批返回；审计只返回最近 500 条；仅用户接口支持姓名/ID 搜索 | 首期如实展示实际范围；服务端筛选/分页单独补齐，不做假分页或虚构总数 |
| 点数调整 | 原因、前后余额、二次确认、expectedBalance 与操作幂等 | 保留这些机制，改善流程与异常恢复 |
| 任务异常 | 仅 review 状态支持核实；确认退款或恢复已保存完整结果 | 保留原任务处理语义，不增加重复调用供应商的“重试”按钮 |
| 配置 | 配置版本校验、历史版本、恢复为新版本、修改原因 | 分组展示、差异核对后提交，不修改历史报价和账本 |
| 成绩模块 | 现有 grades 接口按普通用户身份与学生空间隔离，无平台级成绩管理接口 | 本期维持边界；成绩运维与参照数据发布另立需求 |

代码依据：`backend/public/manage.*`；`backend/src/app/manage/route.ts`；`backend/src/app/api/v2/[...path]/route.ts`；`backend/src/lib/v2/domain.ts`、`model.ts`、`identity.ts`、`legacy.ts`。需求依据为 PRD 顶部已确认修订及第 15 节，旧文档中组织者 Web 工作台的描述不作本期需求。

本地 launch-policy 文件只是一份部署配置来源，不代表线上实时状态。后台当前状态须以管理员接口返回的配置为准。升级不自动开启 AI、改变计价或放宽权限。

## 3. 信息架构与页面安排

桌面采用固定侧栏、紧凑顶栏和主要工作区。侧栏只放六项有实际功能的入口；顶栏显示当前模块、管理员会话与退出，不放宣传语。小屏侧栏收为抽屉，表格在自身区域内横向滚动。

| 模块 | 默认展示 | 按需展开 | 主要操作 |
| --- | --- | --- | --- |
| 运行概览 | AI 状态、进行中/待核实/失败任务入口、冻结点数；必要规模统计降为次级 | 预算和成本说明、规则版本 | 查看待核实任务、进入规则配置 |
| 用户与点数 | 搜索、称呼＋可复制用户 ID、可用/冻结点数、账号/AI 状态 | 用户抽屉内的账本、赠点、关联记录；历史账号认领 | 查看账本、调整点数；权限修改放更多操作 |
| 活动 | 活动名称、发起人标识、收集状态、成员/资料数、AI 状态 | 受限的活动元信息 | 查看关联任务、暂停/恢复该活动 AI |
| AI 任务 | 任务标识、活动、状态、点数、时间；待核实优先可筛选 | 阶段时间、错误、模型用量、估算成本、报价版本等可用字段 | 查看详情；仅符合状态条件时显示核实处理 |
| 规则与预算 | 当前版本、AI 开关、计价摘要、预算摘要 | 计价、预算/并发、输入/存储限额、供应商价格、历史版本 | 编辑指定分组、核对变化、保存新版本 |
| 审计 | 北京时间、操作人、动作、对象、原因 | 关联用户/活动/任务与详情；超出当前返回范围的限制 | 查找关联记录，后续接服务端筛选分页 |

概览只采用有接口依据的指标。可以由已返回任务状态计数得到的待核实/进行中数量可先实现；未接入的日报、趋势、成功率图不以演示数据填充。

用户同名时必须靠用户 ID 区分；复制是辅助操作，姓名不能作为权限或认领依据。活动管理默认只读元信息，不把成员文字、照片、文章正文铺到平台列表。

## 4. 三条优先完成的操作流程

### 用户点数调整

搜索用户 → 打开用户抽屉 → 调整点数 → 填整数与原因 → 核对用户 ID、可用余额前后变化及冻结余额 → 确认提交 → 显示结果与账本。

冻结点数不得被当作可自由扣减余额。按钮提交期间锁定，同一操作的网络重试沿用同一 requestId。余额发生并发变化时保留输入，重新读取并要求核对，不静默按旧余额重算后提交。

### 待核实任务处理

进入待核实列表 → 查看任务阶段、错误和供应商核验依据 → 明确选择“确认未交付并退款”或“恢复已保存完整结果” → 填写原因并核对 → 提交原任务处理 → 回显最新状态及相关流水。

只处理服务端允许的 review 状态；状态变化后重新核对。恢复结果不再次生成文章，不绕过冻结、退款、预算或去重规则。不增加任意退款或一键重新调用模型。

### 规则变更

打开指定分组 → 编辑必要字段 → 填写原因 → 查看仅包含改动字段的前后对照、版本与作用范围 → 确认保存 → 生成新版本并记录审计。

高级价格、容量与并发参数默认折叠。恢复历史配置同样走差异核对，并创建新版本。遇到版本冲突保留本次输入，不覆盖他人的更新。AI 开关的作用范围按服务端规则解释，不承诺停止或退款所有已开始任务。

## 5. 后台 UI 规范

| 项目 | 建议规范 |
| --- | --- |
| 页面背景 | 主体纯白；次级分区中性浅灰；色彩仅用于状态与关键操作 |
| 字号 | 页面标题 24px、分区 20px、正文/表格 16–17px；辅助信息 14–15px，重要数据不压到 12px |
| 字重与行距 | 正文 400、标题 500–600；正文行高约 1.5；长原因/错误允许换行 |
| 表格 | 行高约 56px；主要列固定清晰，ID 可复制；动作最多一项主要入口＋更多 |
| 表单 | 输入值 16–17px；占位提示 14–15px/400；已有标签时不再重复长提示 |
| 按钮 | 主要操作高 44–48px；图标与文字间隔约 8px；居中对齐，不用图标代替危险操作的明确名称 |
| 图标 | 复用小程序 2.3.3 的同套 SVG 轮廓与语义色；网页端封装为可访问组件，不再混用字符箭头/字体字形 |
| 详情容器 | 普通详情右侧抽屉；短确认用对话框；复杂配置使用独立编辑区域 |
| 反馈 | 加载/空态/错误/未授权/会话过期有明确状态；表单错误在字段旁，不只在页面底部显示 |

优先设计并验证“登录、用户列表、用户抽屉、点数二次确认”四个页面/状态，再扩展其余模块。先在 1366px 与 1440px 宽度检查表格、字号、抽屉与长文本，另检查窄屏可用性。视觉确认后进入对应模块实现；本文件不代表这些页面已完成。

## 6. 接口与数据缺口：明确区分现有与新增

| 能力 | 现有接口能做什么 | 需要补充的部分 |
| --- | --- | --- |
| 用户检索与详情 | admin.users 支持姓名/ID 搜索，但整批带 ledger | 状态筛选、服务端分页；按用户获取详情与分页账本，避免列表携带全量账本 |
| 活动/任务检索 | admin.activities、admin.tasks 提供全量元信息 | 时间/状态/用户/活动筛选、分页与稳定排序；详情按明确白名单输出 |
| 审计 | admin.audit 返回最近 500 条 | 服务端时间/对象/动作筛选与分页；不能先截取 500 条再把筛选结果当作全量结果 |
| 预算概览 | 返回累计成本占用与在途预占、配置；服务端已有 budgetUsage 规则 | 增加明确周期、消耗/预占/余量字段，由服务端按实际限额算法计算 |
| 成本说明 | 任务有用量及按模型价格计算的估算信息 | 区分点数、保守成本占用和按用量估算；未对接供应商账单时不标“实际账单金额” |
| 修改后追溯 | 已有原因、审计与幂等机制 | 若要在成功反馈中提供流水/审计链接，需明确返回对应标识，不能在前端猜测关联 |
| 多管理员 | 当前是配置的独立管理员登录，审计 actor 为 platform-admin | 不展示虚构的多管理员名单或细分角色；若需要多人运营，账号与独立审计身份另立任务 |

接口改造保持现有鉴权、余额/配置版本检查和幂等语义，先补契约测试，再接界面。时间筛选还需明确时区：界面显示北京时间，统计周期必须跟实际预算算法一致，不能只把日期标签改成北京时间就声称限额按该时区结算。

## 7. 分阶段执行与验收

以下为单人连续开发的初步工作量估算，非发布日期承诺；接口数据规模与评审反馈可能调整范围。建议总计约 5–8 个工作日。

| 阶段 | 工作 | 交付与验收 | 估算 |
| --- | --- | --- | --- |
| A：视觉与骨架 | UI 规范、共用图标、登录/布局、用户列表与抽屉、确认界面 | 可查看的管理端预览；四个重点状态先评审；不对生产账号做调整演示 | 1–2 日 |
| B：已有业务闭环 | 用户/点数、活动、任务核实、分组配置与恢复、审计、历史认领次级入口 | 测试环境验证调整点数、异常任务、配置冲突与认领流程；完整空态/失败状态 | 2–3 日 |
| C：查询与指标补齐 | 必要的服务端筛选/分页、按需详情、预算周期指标 | 查询结果与真实数据一致，时间和单位明确；不做无业务意义的图表 | 1–2 日 |
| 发布验收 | 权限/并发/幂等回归、浏览器检查、版本与回退记录 | 可审阅版本、变更清单、验证记录和回退路径；生产发布单独执行 | 约 1 日，部分可并行于 B/C |

实施顺序以 A 的页面评审为第一关，后续按模块给预览，不一次铺开所有页面。现有静态管理前端可先模块化整理，不把换框架当作升级前置条件。

### 必须通过的验收项

1. 未登录、普通微信用户、活动发起人均不能调用管理员接口；过期/退出后不继续显示旧敏感详情。
2. 同名用户可区分；列表不暴露原始微信身份凭据；用户和任务详情使用字段白名单。
3. 点数调整必须核对前后余额、提供原因；连续点击和丢响应重试只记一笔；余额冲突不覆盖新值。
4. 配置修改/恢复生成新版本；版本冲突保留输入；历史任务价格与既有账本不变。
5. 任务核实只处理允许状态；恢复交付不产生新供应商调用；不完整结果不能标交付。
6. 页面指标与接口、预算算法、单位和统计周期一致；缺数据时显示真实空态，不填演示数值。
7. 键盘可操作、焦点清晰、对话框可关闭、关闭后回到触发位置；长名称/错误/ID 不撑坏布局。
8. 管理后台不能通过界面改版获取私人学生成绩；不暗示已有全平台成绩管理能力。
9. 本地 UI 验证用隔离数据；上线前保留代码与配置基线，能回退界面版本且不回滚或重写账本。

## 8. 版本与后续候选

管理后台使用独立发布标识，例如拟定 `admin-ui-1.1.0`，不沿用小程序 v2.3.3 的编号来表示后台已经升级。每个交付记录包含 Git 提交、页面/接口范围、测试环境链接、验证结果与回退方式；本次只提交规划文档。

不纳入首期：组织者 Web 工作台、公众号自动发布、多角色权限系统、收费购买点数、批量危险操作、全平台学生成绩查看/修改、无依据的运营大屏。

后续候选需另行明确需求：成绩同步故障的必要元信息查询、参照数据版本的校验/预览/发布与回退、多管理员独立审计身份。尚无接口或授权依据时不先放入口占位。
